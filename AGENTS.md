# Инструкции для работы с Router Configurator

Этот файл относится ко всему репозиторию. Инструкции пользователя имеют приоритет.
Пишите документацию и сообщения пользователю на русском. Перед изменениями изучите
соответствующие модули и README.md; при изменении поведения обновляйте документацию.

## Назначение и структура

Самостоятельный Python-проект (Python 3.10+) для обновления уже настроенных
роутеров Netcraze/Keenetic через RCI. Runtime-зависимости от проекта `ip-addresses`
нет. Адрес роутера приходит в POST-запросе; списка устройств и регистрации нет.

- `router_configurator/app.py` — FastAPI, авторизация, проверка листа и HTTP API.
- `router_configurator/config.py` — конфигурация из `.env` и окружения, скрытие секретов.
- `router_configurator/lists.py` — формат листа, проверка hostname, нормализация записей и разбиение на группы.
- `router_configurator/generator.py`, `generate_geo_domains.py` — отдельный CLI, загрузка и разбор geosite/geoip, атомарная публикация TXT.
- `router_configurator/router.py` — RCI-клиент с отдельной HTTP-сессией на задачу.
- `router_configurator/storage.py` — SQLite, миграции, снимки листов, задачи и события.
- `router_configurator/jobs.py` — обработчики очереди и блокировка каталога данных.
- `router_configurator/logging.py`, `router_configurator/__main__.py` — журнал в stdout и запуск Uvicorn.
- `tests/` — проверки с имитацией сети и роутеров.
- `Dockerfile`, `compose.yaml`, `deploy/router-configurator.service` — развёртывание.

## Контракты и совместимость

- Все маршруты API требуют `X-API-Key`; сравнение ключа — через `secrets.compare_digest`.
- `POST /api/v1/router-configurations` принимает строго `hostname` и `action: "update"`.
  После проверки и сохранения снимка возвращает `202`, `job_id`, `status: "queued"` и `status_url`.
- `GET /api/v1/jobs/{job_id}` возвращает состояние, время, результат и события;
  неизвестная задача — `404`.
- `GET /api/v1/list/version` перечитывает настроенный лист и возвращает
  `{"version":"..."}` или `{"version":null}` для старого формата. Не создаёт задач,
  не обращается к роутерам; успешный ответ имеет `Cache-Control: no-store`.
- Ошибки авторизации — `401`, валидации запроса — `422`, недоступный, пустой или
  некорректный лист — `503` без постановки задачи.
- IP без схемы использует HTTP, домен — HTTPS. Допустим базовый HTTP(S) URL с портом;
  учётные данные, путь, query и fragment в адресе роутера запрещены.
- Новые TXT начинаются с `version: <дата и время ISO 8601 в UTC с микросекундами и Z>`,
  затем `mode: proxy` или `mode: direct`, далее домены и IP/CIDR.
  Старые листы и снимки без версии должны оставаться читаемыми.
- Пресеты начинаются с `mode:` и поддерживают `geosite:`, `geoip:`, `domain:`.
  Версию добавляет генератор; IPv6 по умолчанию исключается. Сохраняйте нормализацию,
  порядок после удаления дубликатов и предел 299 записей на группу.
- Генератор полностью проверяет результат перед атомарной заменой файла.
  Ошибка сохраняет предыдущий TXT вместе с его версией.

## Очередь и RCI

- Один процесс Uvicorn и пул обработчиков `MAX_PARALLEL_JOBS` (1–32, по умолчанию 4).
  Сетевые операции выполняются вне HTTP event loop.
- Разные роутеры обновляются параллельно, один нормализованный hostname —
  последовательно, независимо от регистра, схемы и порта. Выбор задачи атомарен
  в SQLite; блокировка данных защищает от второго экземпляра службы.
- Снимок листа, включая версию, сохраняется до ответа `202`. Перегенерация файла
  не изменяет ожидающие или выполняемые задачи.
- После перезапуска `queued` продолжаются, оставшиеся `running` становятся `failed`
  с причиной прерывания и автоматически не повторяются. Миграции сохраняют историю.
- При остановке прекращается выбор новых задач. Общий срок ожидания обработчиков —
  885 секунд; Compose и systemd дают 900 секунд.
- `update` заменяет **все** существующие списки и DNS-маршруты. До изменений проверяются
  нужные интерфейсы, затем отключается WireGuard, настраивается приоритет WAN,
  заменяются списки/маршруты и включается выбранный WireGuard.
  Сохраняйте ограниченные повторы, таймауты и проверку применения команд.
- Не заменяйте исключения RCI на `sys.exit`, не вводите общую HTTP-сессию для задач.
  Установка WireGuard, смена VPN endpoint и автоматический откат не входят в текущий API.

## Конфигурация, данные и журнал

- Конфигурация читается при запуске, лист — при каждом POST и GET его версии.
  Относительные пути конфигурации считаются от `.env`, переменные окружения имеют приоритет.
- Не выводите секреты из `.env`, HTTP-заголовки, тела запросов/ответов RCI или полный
  снимок листа. Применяйте `Config.redact`; неожиданные исключения не должны раскрывать
  секреты через traceback. Сохраняйте контекст `job_id`, hostname и статуса в журнале задач.
- Не включайте `.env`, `.data`, `.cache`, `lists/` или SQLite в Git и Docker-образ.
  `.env.example` содержит только шаблонные значения.
- Данные Docker хранятся в `./.data` рядом с `compose.yaml` через bind mount, а не
  named volume. `.env` и весь каталог `lists` подключаются только для чтения;
  подключение каталога позволяет видеть атомарную замену TXT.
- Проверки генерации пишите в отдельный временный каталог или `.cache/`.
  Не перезаписывайте рабочий лист, пресеты пользователя или рабочую SQLite ради теста.
  При необходимом переносе данных сохраняйте резервную копию и историю задач.

## Проверки и команды

Используйте существующее `.venv` и зависимости из `requirements-dev.txt`.
На Windows команды выполняются в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m router_configurator --env-file .env
```

На Linux:

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
.venv/bin/python -m router_configurator --env-file .env
```

Проверка Compose и применение изменений кода:

```bash
docker compose config --quiet
docker compose up -d --build router-configurator
docker compose logs -f router-configurator
```

Если Docker требует sudo, добавляйте его к этим командам. Проверку systemd выполняйте
на Linux; успешная сборка Docker не подтверждает работоспособность systemd unit.

Автоматические тесты не обращаются к реальным роутерам и не скачивают базы:
`tests/conftest.py` запрещает сетевые вызовы; используйте имитации RCI и загрузки.
Для живой проверки учитывайте разрешение пользователя и уже согласованный hostname;
не расширяйте её на другие устройства. Повторного подтверждения ранее разрешённой
проверки не требуется.

Для функциональных изменений проверяйте затронутые сценарии: авторизацию, формат
листа и версии, генерацию онлайн/офлайн на имитациях, сохранение файла при ошибке,
очередь и снимки после перезапуска, параллелизм, сбои RCI и отсутствие секретов в журнале.
Изменения только документации не требуют запуска тестов. Проверяйте реальное поведение,
не добавляйте тесты, которые лишь повторяют реализацию.
